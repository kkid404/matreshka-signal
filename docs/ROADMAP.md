## Текущая структура `src` (как устроено сейчас)

```text
src/
  application/         # Use-cases: orchestration бизнес-сценариев (replay, catalog, config)
  core/                # Домен и базовая логика: модели, конфиг, индикаторы, уровни, probability, detector, data_fetcher
  infrastructure/      # Интеграционные клиенты/кодеки (notification/signal-engine HTTP clients)
  services/            # Отдельные сервисы/entrypoints: control-bot, signal-engine-service, notification-service
  strategies/          # Набор торговых стратегий + registry
  main.py              # Scanner runtime (single/daemon/replay CLI)
  telegram_notifier.py # Telegram Bot API gateway (используется notification-service)
```

### Кто за что отвечает

- `core` — **чистая логика и модели**, без привязки к конкретному процессу/сервису.
- `application` — **сценарии уровня приложения** (какие шаги и в каком порядке запускать).
- `infrastructure` — **внешние границы**: HTTP-клиенты, сериализация, протокольные адаптеры.
- `services` — **долго живущие процессы** (HTTP/бот), которые используют `application` + `infrastructure`.
- `strategies` — **алгоритмы сигналов**; не должны знать про Telegram/HTTP/CLI.

### Как масштабировать дальше (правила)

1. Новая бизнес-логика → сначала в `core`, затем orchestration в `application`.
2. Новый внешний канал/интеграция (API, broker, queue) → `infrastructure`.
3. Новый отдельный процесс/микросервис → `services` + отдельный контейнер в `docker-compose`.
4. `main.py` держать тонким (CLI + wiring), без разрастания доменной логики.
5. Стратегии добавлять только в `strategies/` и регистрировать в `strategies/__init__.py`.
6. Перед переносом модулей между папками: сначала перевести импорты, потом удалять старые файлы.

### Технический ориентир по фазам роста

- Ближайшая цель: вынести scan-orchestration из `main.py` в `application` (thin-runner).
- Затем: выделить `market-data-service` (кэш свечей + контроль лимитов).
- Далее: перейти к событийной шине (`signal.created`) для развязки engine/notification/analytics.
