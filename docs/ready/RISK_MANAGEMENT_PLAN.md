# План: расчёт суммы входа по стоп-лоссу (Risk Management)

Цель: внедрить профиль трейдера и рассчитывать рекомендуемый размер входа (position size) на основе риска и дистанции до стоп-лосса.

---

## 1) Scope MVP

В MVP реализуем:

- профиль трейдера, связанный с `telegram user_id`;
- базовый риск-подход **fixed % risk per trade**;
- расчёт `recommended_position_size` для сигнала (`entry`, `sl`);
- отображение расчёта в карточке сигнала в Telegram;
- базовые ограничения (валидация, округление, минимальный лот).

Не включаем в MVP:

- автоматическое открытие сделок;
- продвинутую портфельную оптимизацию;
- динамический риск по волатильности/серии убытков.

---

## 2) Модель данных профиля трейдера

Минимальный набор полей:

- `user_id: int` — Telegram user id (ключ профиля)
- `budget_usdt: float` — доступный капитал для расчёта риска
- `risk_per_trade_pct: float` — риск на одну сделку, % от бюджета (например, 0.5–2.0)
- `max_open_positions: int` — лимит одновременных позиций
- `daily_risk_limit_pct: float` — дневной лимит суммарного риска
- `default_leverage: int | None` — опционально, для справки в карточке
- `is_active: bool` — профиль включён/выключен
- `updated_at: datetime`

Рекомендация по хранению (MVP):

- файловое хранилище `data/risk_profiles.json` (аналогично текущим простым persisted-настройкам);
- интерфейс репозитория для будущей миграции в БД без изменений бизнес-логики.

---

## 3) Формулы риск-менеджмента

### 3.1 Основная формула

1. `risk_amount_usdt = budget_usdt * (risk_per_trade_pct / 100)`
2. `stop_distance = abs(entry_price - stop_loss_price)`
3. `position_size_units = risk_amount_usdt / stop_distance`

Для линейных USDT-контрактов (где PnL примерно линейно зависит от цены) этого достаточно для базового расчёта размера.

### 3.2 Ограничения

- если `stop_distance <= 0` → расчёт невозможен;
- если `position_size_units` после округления `< min_qty` → сигнал помечается как "size too small";
- если риск после округления вверх превышает `risk_amount_usdt` → округлять вниз;
- учитывать `qty_step` и `min_notional` (если доступны из market metadata).

### 3.3 Вывод в карточку

Показывать:

- `Budget`
- `Risk per trade`
- `Risk amount (USDT)`
- `Entry / SL / TP`
- `Recommended size`
- `Estimated loss at SL`

## 4) Telegram UX

Команды MVP:

- `/risk_profile` — показать текущий профиль
- `/set_budget <amount>` — установить бюджет (например, `/set_budget 1000`)
- `/set_risk <percent>` — установить риск на сделку (например, `/set_risk 1.0`)
- `/set_limits <max_positions> <daily_risk_pct>` — лимиты (например, `/set_limits 3 4`)
- `/risk_help` — краткая справка по формулам и ограничениям

Требования к UX:

- понятные ошибки валидации;
- подтверждение успешно сохранённых параметров;
- безопасные дефолты при первом запуске (например, `risk_per_trade_pct=1.0`, `max_open_positions=1`).

---

## 5) Интеграция в pipeline сигналов

1. При формировании сигнала проверить наличие активного профиля для пользователя.
2. Выполнить `position sizing` по `entry/sl`.
3. Добавить блок risk-management в `SignalCard`/Telegram payload.
4. Если расчёт невозможен (edge-case) — отправить сигнал с причиной и без рекомендованного размера.

---

## 6) Edge-cases

- `entry == sl` или слишком близкий SL;
- нулевой/отрицательный бюджет;
- риск вне разумных границ (например, `<0.1%` или `>5%` для MVP);
- отсутствие market limits (`qty_step`, `min_qty`) — fallback с консервативным округлением;
- слишком маленький размер позиции для биржи.

---

## 7) Тестирование

### Unit

- корректность формулы `risk_amount` и `position_size`;
- округление и лимиты (`qty_step`, `min_qty`);
- edge-cases (`stop_distance <= 0`, invalid profile values).

### Integration

- Telegram команды профиля (`/set_budget`, `/set_risk`, `/risk_profile`);
- появление блока risk-management в карточке сигнала;
- корректное поведение при отсутствии профиля.
